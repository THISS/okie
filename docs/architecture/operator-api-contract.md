# Operator workflow HTTP contract

Implementation contract for CLA-133/CLA-135. These routes are not yet wired. All identifiers come from `apps/server/src/operatorContracts.ts`; the controller must not expose credentials or internal filesystem paths.

## Routes

| Method and route | Request | Response |
| --- | --- | --- |
| GET `/api/operator/session` | GitHub session cookie if present | `{ operator: boolean }`; no allowlist disclosure |
| GET `/api/operator/runs` | Operator session | `{ runs: OperatorRun[] }`, newest first, bounded |
| POST `/api/operator/runs` | `{ url, idempotencyKey }` | 202 `{ run, deduped }`; normalize public GitHub input with existing parser |
| GET `/api/operator/runs/:runId` | Operator session | `{ run, draft?, attempts, events, usage }` |
| POST `/api/operator/runs/:runId/cancel` | Empty object | `{ run }`; durable cancellation checked before further work |
| GET `/api/operator/drafts/:draftRevisionId` | Operator session | `{ draft, source, scopes, usage, currentPublicationVersionId? }` |
| GET `/api/operator/drafts/:draftRevisionId/bundle` | Operator session | Valid portable atlas JSON for the immutable selected revision |
| POST `/api/operator/drafts/:draftRevisionId/retry` | `{ scopeId }` | 202 `{ run, draftRevisionId }`; selected scope only |
| POST `/api/operator/drafts/:draftRevisionId/refresh` | `{ scopeIds }` | 202 `{ run, draftRevisionId }`; explicit stale scopes only, run as one batch-retry pass (shared ancestors re-reduce once, one revision installed) |
| POST `/api/operator/drafts/:draftRevisionId/publish` | `{ expectedCurrentVersionId?, acknowledgeCoverage }` | `{ publication }`; 409 `code: "publication_stale"` on stale current pointer/revision |
| POST `/api/operator/repositories/:repositoryId/incremental` | `{ ref?, autoPublish? }`; `:repositoryId` is `repo:owner/name` or `owner/name`, URL-encoded | CLA-271 "Update to latest commit". Answers without awaiting GitHub or the scan: 202 `{ status: "started", runId, baselineCommitSha, commitSha? }` (`commitSha` only for a full-SHA `ref`; the runner resolves anything else and records up-to-date itself); 200 `{ status: "up_to_date", commitSha, baselineCommitSha }` only for a full-SHA `ref` equal to the baseline; 409 `{ status: "active", runId, code: "run_active" }`; 422 `code: "no_baseline"` or invalid `ref`; any other failure is 500 with a generic message; 404 unknown repository. `autoPublish: true` is the only per-request auto-publish opt-in (session-authenticated) |
| POST `/api/operator/cron/incremental` | `Authorization: Bearer $OKIE_INCREMENTAL_CRON_TOKEN`; `{ repositoryId?, ref? }` (≤ 16 KB) | No session. Method, configuration and token are checked before the body is read: 404 unless the token is configured (or not POST), 401 on a wrong token, 413 over the size cap. Auto-publish follows only `OKIE_INCREMENTAL_AUTO_PUBLISH`; a body `autoPublish` is ignored. 200 `{ results: [{ repositoryId, status, ... }] }`, one entry per published repository (or the named one), each shaped like the route above |
| POST `/api/operator/webhooks/github` | GitHub `push` event, `X-Hub-Signature-256`, `X-GitHub-Delivery` (≤ 5 MB) | No session. 404 unless `OKIE_GITHUB_WEBHOOK_SECRET` is set (checked with the method before the body is read), 413 over the size cap, 401 `signature_invalid`. The push is only a trigger: the debounced start resolves the default branch HEAD at fire time, never the pushed SHA. 202 `{ scheduled: true, repositoryId, pushedCommitSha, debounceMs }`; 200 `{ ignored: "event" \| "branch" \| "repository" \| "commit" \| "duplicate_delivery" }`. Auto-publish follows only `OKIE_INCREMENTAL_AUTO_PUBLISH` |

Errors carry a stable machine-readable `code` next to the display-only `error` text; clients decide on the code, never the text: 401 `session_expired` (no verified session), 403 `not_operator` (signed in, not on the allow-list — e.g. removed mid-session) or `csrf_rejected`, 409 `run_active` (a pass is queued/running) or `draft_superseded` (with `currentDraftRevisionId`) on retry/refresh, and 409 `publication_stale` on publish.

A scope with no attempt on the requested revision lists the run's latest attempt for it from an earlier revision of the same run (a full run's attempts live on its pre-enrichment draft; a retry's on the revision it started from), so its error stays visible. That lineage attempt is marked `inherited: true` and never changes the scope's state or metrics (the web client skips it when summing tokens, cost, and latency).

Scope rows include identity/parent/name, C4 `kind` and `depth`, an optional `path` (the scope's primary repository-relative source path, from its first source ref; used for operator list search and tooltips, never a server filesystem path; absent when the scope has no source ref or on older servers), an optional operator-only `metrics: { costUsd?, totalTokens?, updatedAt? }` summary of the attempts behind the scope's current state (this draft's attempts for the scope when it has any, else the attempt an enriched sidecar's explanation row names — those live under the pre-enrichment draft — plus the row's install time; cost is measured, else estimated; omitted when nothing is known, and never included on public read routes), latest attempt state, accepted explanation/version/evidence, stale flag and validation diagnostics. Usage distinguishes measured cost, estimated cost and unknown cost. Events have stable IDs and can be paginated; an unbounded complete log should not be returned by default.

## Incremental runs (CLA-271)

An incremental run is its own run: `kind: "incremental"` and `incremental: { baseline: { runId, draftRevisionId, artifactRevisionId, publicationVersionId?, commitSha }, ref?, targetCommitSha?, upToDate?: { commitSha }, trigger: "operator" | "cron" | "webhook" | "script", autoPublish? }`. `source.commitSha` is the new commit once scanned; `targetCommitSha` is the resolved target as soon as it is known (at start, else when the run resolves it).

The baseline is a chain on the current publication: the newest reviewable (`awaiting_review` or `complete`) incremental draft whose `baseline.publicationVersionId` is the current publication, else that publication's own draft; without a publication, the most recently created reviewable run's draft. So A→B→C diffs C against B and reuses B's re-enrichment, and a manual publish restarts the chain from it. The next step re-seeds (`carried`) only the scopes the previous unpublished chain step left failed, not run, or stale without a reason; gaps inherited from the publication are never re-seeded. Commit-caused seeds are admitted first, and carried seeds run in a second pass only when the first pass stopped `complete`. A step failed a scope when it attempted it and the scope is still unfinished in that step's final sidecar; a scope two consecutive steps failed is dropped (`dropped`), together with every ancestor it holds stale, and is not carried again until a commit touches it or the operator refreshes it. `publicationVersionId` always names the publication under the chain; auto-publish expects it to still be current. If queueing a started run throws, the run is marked `failed` ("The incremental run could not be queued.") before the error propagates. Starting never touches the network or awaits the scan: the route answers `active` (409) while any run of the repository is active, `up_to_date` (200) only when the given ref is a full SHA equal to the baseline's, and otherwise 202 `started` (no `commitSha`: the runner resolves the ref). An up-to-date run found by the runner records `incremental.up_to_date`, sets `incremental.upToDate`, ends `complete` with no draft, and deletes the repository's earlier up-to-date no-op runs (no draft revision; their events go too), so `GET /api/operator/runs` keeps one per repository. Draft detail also carries `currentPublicationDraftRevisionId`. After its passes, an incremental run's `error` (if any pass reported one) is rewritten in the changelog outcome's numbers: `Update stopped at the run budget (OKIE_LLM_OPERATOR_*): 15 re-summarised, 19 not run, 52 kept stale (changed; not re-enriched).` A debounced webhook start records `incremental.webhook_fire` (`status`: `started`, `up_to_date`, `active`, `failed` with a generic `reason`) on the repository's newest run. A run cancelled while queued never starts. Other events: `incremental.diff` (counts), `enrichment.finished` with `pass: "incremental"`, `incremental.auto_publish` (`published`, `reason`), `incremental.finished`.

Draft detail for an incremental revision adds `incremental` (the run info above) and `changelog`. Scope rows can carry `staleReason: "dependency-internal"` (a claim re-check: a dependency, or the module that declares it, changed only internally), `"moved"` (evidence lines moved) or `"changed"` (a below-cap scope that has an explanation, whose own source or relations changed, or that consumes an entity with a surface change; the pass never re-enriches below the cap, so its explanation is kept but marked stale and blocks auto-publish). An explained below-cap consumer of an internally changed entity gets `"dependency-internal"`. In draft detail only, a stale scope without an overlay reason gets `"pending"` (selected by this update, not re-enriched: budget stop or failure; the next update retries it), `"dropped"` (the carry gave up on it) or `"inherited"` (left unfinished before this chain; Refresh it); these are presentation reasons, not sidecar overlays, so such a scope still holds its parents stale. No reason holds a parent stale. Every list is `{ total, items }`, with at most 50 items:

```jsonc
{
  "schemaVersion": 1, "fromCommit": "<sha>", "toCommit": "<sha>",
  "baseline": { "runId": "…", "draftRevisionId": "…", "publicationVersionId": "…" },
  "cap": "component",
  "counts": { "entitiesAdded": 0, "entitiesRemoved": 0, "entitiesChanged": 1, "surfaceChanges": 0, "internalChanges": 1, "entitiesMoved": 0,
              "relationsAdded": 0, "relationsRemoved": 0, "removedExports": 0, "dirty": 3, "carried": 0, "stale": 1, "unfinished": 0, "reused": 1, "removedScopes": 0 },  // stale includes unfinished
  "entities": { "added": { "total": 0, "items": [{ "id", "kind", "name" }] }, "removed": {…}, "changed": { "items": [{ "id", "kind", "name", "change": "surface" | "internal" }] }, "moved": {…} },
  "relations": { "added": { "items": [{ "from", "to", "kind" }] }, "removed": {…} },
  "removedExports": { "items": [{ "id", "kind", "name", "consumerCount": 3 }] },
  "stale": { "items": [{ "scopeId", "reason": "dependency-internal" | "moved" | "changed" }] },  // every scope stale with a reason in this revision, inherited ones included
  "dirty": { "items": [{ "id", "kind", "name" }] },     // commit-caused only
  "carried": { "items": [{ "id", "kind", "name" }] },   // re-seeded from the previous chain step
  "unfinished": { "items": [{ "id", "kind", "name", "reason": "pending" | "dropped" | "inherited" }] },  // stale without a reason, or dropped by the carry
  "publication": { "versionId", "commitSha", "draftRevisionId", "artifactRevisionId" },
  "chain": [{ "runId", "draftRevisionId", "toCommit" }],  // earlier unpublished steps, oldest first; the last 20 only
  "chainLength": 1, "chainPartial": true,               // total earlier steps; partial = a lower bound (the chain passes a legacy draft)
  "cumulative": { "fromCommit": "<publication sha>", "toCommit": "<sha>", "counts": {…}, "entities": {…}, "relations": {…}, "removedExports": {…}, "dirty": {…} },
  "reuse": { "fromPublication": {…}, "sincePublication": {…} },
  "hashCheck": { "checked": 1, "mismatches": 0, "unknown": 0 },
  "outcome": { "state": "pending" | "settled", "resummarised": {…}, "resummarisedByKind": { "component": 1, "container": 1, "softwareSystem": 1 },
               "keptStale": {…}, "failed": {…}, "notRun": {…} },
  "summary": "1 changed; container demo-lib re-summarised; 1 component re-summarised; system re-summarised; 1 stale; 1 reused",
  "cumulativeSummary": "since published abc1234 (2 updates): 5 changed; 14 re-summarised since publication (unreviewed); 2 stale; 230 reused from publication"
}
```

The diff part is stored in the revision's immutable artifact (`incremental-changelog.json`). `outcome` and `summary` are derived from that same revision's sidecar. `outcome.state` is `"pending"` while the run's pass is still writing to the revision. `resummarised` lists dirty scopes that got a new explanation. `keptStale` lists dirty scopes that still carry their baseline explanation, marked stale (refused, failed or skipped by the pass). The outcome covers dirty and carried scopes.

`cumulative` is the publication → this commit diff, computed by the same pure function over the publication's snapshot, and is present only on a draft chained on a publication. `reuse` splits reused explanations into `fromPublication` (byte-for-byte the published explanation) and `sincePublication` (re-enriched by an earlier unpublished step, not yet reviewed); a stale or unfinished scope is in neither (it is listed as stale or unfinished). The stored artifact also keeps `dropped` (the carry's dropped scopes, unbounded); the response folds it into `unfinished`. The review panel defaults to the cumulative view ("Published abc1234 → this draft def5678 (2 updates)", "≥N updates" for a partial chain, flagged "no longer the live publication" when `currentPublicationVersionId` differs) with "This update only" as the secondary view.

`hashCheck` is report-only: a mismatch between a reused explanation's recomputed input hash and its stored hash is counted, never fails the run and never triggers re-enrichment, and `PROMPT_VERSION` was not bumped for CLA-271 (drafts made before the commit-invariant hash show mismatches there).

**Change classification.** An entity is `changed` when its excerpt text, exposure, name, kind, parent, tags or technology differ; `moved` when only line positions differ. A change is `surface` when the declaration signature or exports changed, else `internal`. For code, interfaces, type aliases, enums, classes, structs, traits, impls and object literals compare their whole excerpt (every member is surface); a function's signature is its head through the body `{` at bracket depth 0 after the parameter list closes, with `<`/`>` depth tracked throughout (generic constraints, multi-line parameters and a return type on later lines included; in a Rust `where` clause, rustfmt style too, the first depth-0 `{` is the body). TypeScript overload heads are compared together, so a change to any overload is surface. Non-code entities have no declaration signature: their surface is their exposure and their code children. Surface changes dirty 1-hop consumers of the entity and its module; internal changes mark them stale. **Known limitation:** excerpts are capped at 48 lines and the scan artifacts carry no per-file content hash or blob SHA, so a change below an excerpt's cap (inside a long function or file) is invisible to the diff and its scopes are reused.

## Access and publication rules

- Only the session probe is publicly readable. All remaining operator routes, including bundles, reject unsigned callers with 401 and non-operators with 403 before revealing existence or metadata.
- Cookie-authenticated mutations require the explicit configured public Origin. The operator access helper ignores forwarded host headers; configuration must name the actual browser origin behind a proxy.
- Existing `/api/scans` submission/list/detail routes must no longer provide an alternate non-operator path into hosted scans or draft metadata. Preserve the public atlas read routes, not self-service submission behavior.
- No draft contents are served below `/scan/`. The public bootstrap resolves an immutable publication reference and carries that reference through neighborhood, excerpts, source, scene/story and embed metadata. Do not bind those resources only to the source SHA: enrichment versions can share a commit.
- A current-version switch is atomic. Retained published artifacts may service version-pinned in-flight reads; this is resource consistency, not a public version-history listing. Retention/access policy must be explicit before deployment. Draft and unpublished artifact IDs never grant public access.
- Publish must validate the complete artifact and freeze the selected draft revision. Acknowledged incomplete, failed or stale enrichment may publish; stale explanations remain labelled. Later completions create another draft.
- Publishing errors do not expose storage paths or corrupt the prior public version. Read current publication after a conflict so the UI can refresh its review context.

## UI integration

An operator workspace owns run administration and preview. Draft previews use the captured portable bundle and existing atlas/source/diagram components; they do not replace the public atlas or browser-persist the draft into the user's unrelated local portable viewer. Selecting a draft revision pins its preview until the operator chooses a newer revision.

The normal public repository URL continues to show the latest published atlas. Ask Atlas and public history browsing are unchanged by this contract.
