# Deterministic ingestion golden-test contract

Status: QA acceptance contract for the boundary proposed in
[`deterministic-first-ingestion.md`](./deterministic-first-ingestion.md).

This document defines what must be byte-reproducible, what must merely be
replayable, and which metadata is required before ingestion output can be
cached or published. It is intentionally independent of a database, queue, LLM
provider, or orchestration framework.

## Reproducibility classes

Every ingestion result declares one of these modes:

- `deterministic` — no live model output participates. The same pinned inputs,
  configuration, schemas, and tool versions must produce byte-identical
  canonical output and hashes.
- `recorded-replay` — a previously captured model response is an explicit
  immutable input. The same response bytes and deterministic inputs must
  produce byte-identical accepted output and hashes.
- `live-enrichment` — the model response may vary even with a provider seed.
  Reproducibility begins at the captured response boundary: every request and
  response is hashed, and replaying that exact response must be byte-identical.
  A later response never overwrites or reuses the cache entry of an earlier
  response merely because the request was the same.

Timestamps, latency, token counts, and cost are audit data. They must not enter
the semantic content hash. If an audit-envelope hash is required, it is a
separate named hash.

## Stable identity contract

Stable logical IDs are generated by deterministic host code, never by an LLM,
discovery order, database sequence, or display name.

- Canonical repository identity and immutable commit/tree identity scope every
  scan.
- Source identities use normalized repository-relative path, commit, symbol,
  and line range. Absolute workstation paths are forbidden.
- Entity identities derive from a versioned extractor namespace plus canonical
  language/kind/symbol identity. A rename or move policy must be explicit; it
  must not be inferred from array position.
- Claim fingerprints cover subject identity, predicate, canonical value,
  provenance class, deterministic derivation rule/version, and sorted input
  claim fingerprints.
- Persisted row IDs are snapshot-qualified even when the logical fingerprint is
  unchanged across snapshots. Cross-snapshot references are invalid.
- If two candidates have the same base identity, collision suffixes are
  assigned after sorting by canonical source identity. Reversing traversal order
  cannot reverse suffix assignment.
- Explanations receive host-generated IDs from their snapshot, supporting claim
  fingerprints, prompt policy, and response hash. Model-suggested IDs are data,
  not authority.

Golden tests must prove unchanged facts retain logical fingerprints across a
rescan, while changed source/value/rule inputs produce a different fingerprint.

## Canonical serialization

Canonical artifacts use one documented profile, preferably RFC 8785 JSON
Canonicalization Scheme, with these repository rules:

- UTF-8 text normalized to NFC and line endings normalized to LF.
- Repository paths use `/`, are relative, contain no `.`/`..` traversal, and
  have a documented case-sensitivity policy.
- Object keys are canonicalized by the serialization profile.
- Arrays representing sets are deduplicated and sorted by stable ID. Arrays
  whose order is semantic, such as story steps or source ranges within a single
  excerpt, preserve their declared order.
- Numbers must be finite; `-0` normalizes to `0`; confidence and line ranges are
  range-validated before serialization.
- Unknown fields are rejected in signed/cacheable core records or retained only
  in a versioned `extensions` namespace. They are never silently discarded and
  re-hashed as though the input were understood.
- Volatile audit fields are excluded from the semantic artifact rather than
  removed opportunistically during hashing.

Randomizing filesystem discovery, parser callback, worker completion, map
insertion, database row, and LLM citation order must not change canonical bytes.

## Evidence and derivation provenance

Every published `observed` or `inferred` claim must pass all applicable gates:

- Every source reference resolves inside the pinned repository/dependency input
  and uses that exact immutable revision.
- File, symbol, and line ranges are valid for the captured source bytes.
- Observed claims record extractor name/version and the source-content hash.
- Inferred claims record rule name/version, sorted input claim IDs, and retain
  the transitive source references required to inspect the derivation.
- Confidence is absent for observations. An inference confidence is finite,
  calibrated, and in `[0,1]` when present.
- An explanation cites existing accepted claim IDs only. Its prose is never
  inserted into `sourceRefs` or promoted to observed evidence.
- Missing evidence is an explicit validation/quarantine state, not an empty
  successful claim with implied confidence.
- A changed/disappeared supporting fingerprint invalidates or marks stale every
  dependent inference and explanation. Carry-forward records why regeneration
  was skipped and which fingerprints were unchanged.

The golden corpus includes path traversal, stale commit, missing symbol,
out-of-range lines, dangling input claim, evidence cycles, and explanation text
masquerading as evidence.

## Hash and cache domains

Use SHA-256 or a stronger documented digest. Every digest has a domain/version
prefix so two artifact types cannot share an accidental cache namespace.

At minimum record:

1. `inputManifestHash` — repository commit/tree, pinned dependencies/submodules,
   include/exclude rules, scan configuration, redaction policy, schema versions,
   extractor/parser binaries and versions.
2. `deterministicFactsHash` — canonical observed claims and deterministic
   inferences.
3. `enrichmentPacketHash` — the exact bounded/redacted claim/excerpt packet sent
   for enrichment.
4. `promptTemplateHash` and `outputSchemaHash`.
5. `modelRequestHash` — provider, exact model/version, decoding parameters,
   optional seed, tool definitions, prompt and packet hashes.
6. `rawModelResponseHash` for every attempt.
7. `acceptedEnrichmentHash` — canonical validated explanation/proposal output.
8. `semanticSnapshotHash` — the published deterministic graph plus accepted
   enrichment references, excluding volatile audit data.

A cache hit requires every field in its documented cache-key domain to match.
Changing schema, extractor, rule, redaction, prompt, model, decoding parameter,
supporting claim fingerprint, or review policy must miss the affected cache.
Changing only request time or billing metadata must not.

Cache tests must also prove that failures, partial writes, rejected model output,
and unreviewed proposals cannot poison a later valid entry.

## Structured LLM boundary

The model receives bounded redacted inputs and returns data validated against a
versioned strict schema before any normalization or persistence:

- `additionalProperties: false` for core records; enums, lengths, counts,
  nesting depth, numeric ranges, and total decoded bytes are bounded.
- Citations can reference only IDs present in the supplied packet. The model
  cannot create an observed claim, change an observed value, choose canonical
  IDs, or cite arbitrary paths/URLs as repository evidence.
- Duplicate IDs/citations are rejected or deterministically deduplicated by the
  documented schema policy.
- Schema, semantic-reference, grounding, and policy validation are separate
  named outcomes in audit metadata.
- Invalid output is applied atomically: zero model-authored records are
  published. The deterministic snapshot remains publishable.
- Retries are bounded. Each attempt stores request/response hashes, provider
  metadata, validation result, and retry reason. A repair prompt is a new prompt
  hash, not the same request.
- Raw prompts/responses are access-controlled audit artifacts with retention and
  secret-handling policy; their contents are not exposed through public URLs or
  inspector markup.

The invalid-output corpus includes malformed JSON, unknown fields, excessive
depth/size, non-finite numbers, unknown claim IDs, prompt injection strings,
attempted observed-value mutation, invented evidence, and mixed valid/invalid
records.

## Required reproducibility metadata

Every published snapshot records:

- ingestion contract/schema/generator version;
- repository identity, commit SHA and tree hash;
- dependency/submodule revisions;
- normalized scan configuration and redaction-policy hash;
- extractor, parser, deterministic rule, and compiler names/versions;
- input, deterministic-facts, semantic-snapshot, and relevant cache hashes;
- reproducibility mode;
- for each enrichment attempt: provider, exact model identifier/version when
  supplied, decoding parameters, seed support/value, prompt/schema/packet/request
  and response hashes, validation result, review state, and generation time;
- prior snapshot/fingerprint lineage and carried-forward explanation metadata.

If a provider cannot supply a stable model revision or deterministic seed, that
limitation is explicit metadata. It must never be represented as deterministic.

## Golden fixture matrix

| Fixture | Mutation | Required result |
|---|---|---|
| Small pinned repository | Repeat unchanged | Canonical bytes and every deterministic hash identical |
| Discovery order | Reverse/shuffle files, symbols, relations, worker completion | Identical IDs, order, bytes and hashes |
| Platform | macOS/Linux path separators, locale and timezone | Identical canonical artifact |
| Unicode | Composed/decomposed names | NFC-equivalent identity and bytes |
| Identity collision | Same base symbol identity in multiple sources | Stable sorted suffixes independent of traversal |
| Rescan unchanged | New scan time only | Same logical fingerprints; audit time differs |
| Rescan change | Change source/value/rule version | Affected fingerprints change; dependents stale; unrelated claims unchanged |
| Evidence | Move/missing/invalid source range or commit | Atomic validation failure/quarantine with exact issue path |
| LLM replay | Same captured response, randomized citation order | Identical accepted canonical output/hash |
| LLM live | Same request, different valid response | Distinct response/accepted hashes; no cache overwrite |
| LLM invalid | Each invalid-output corpus case | Zero partial apply; deterministic snapshot still publishable |
| Cache | Vary each key component one at a time | Required hit/miss behavior for that domain |
| Failure | Model timeout, budget stop, extractor failure, process restart | No partial published snapshot; resumable stage state; deterministic-only publication when valid |

For each golden fixture, commit the canonical expected artifact and a manifest of
expected hashes. Tests compare bytes, not only parsed object equality.

## Release gates

The ingestion boundary is not ready for credit-bearing scans until:

1. deterministic and recorded-replay fixtures are byte-identical over at least
   100 randomized traversal/execution orders;
2. stable-ID collision and rescan lineage tests pass;
3. all published claims pass evidence/derivation validation;
4. every cache key has a one-field-at-a-time hit/miss test;
5. the strict LLM invalid-output corpus proves atomic rejection;
6. live enrichment records complete reproducibility limitations and can be
   replayed exactly from captured response bytes;
7. scan interruption cannot expose a partial immutable snapshot or consume
   enrichment credits twice for the same committed request hash;
8. logs, URLs, telemetry, and public exports contain no raw prompts, secrets,
   absolute source paths, or private excerpt content.
