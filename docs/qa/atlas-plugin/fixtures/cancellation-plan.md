# User-facing plan

Ask currently runs from the App through `submitAskQuestion` to `/api/ask`, where the server admits retrieval work, calls the answer orchestrator, and may persist an authenticated answer. Implement cancellation first as an explicit request-lifecycle contract: closing the panel or replacing its map cancels the pending turn, prevents late UI updates, and permits a fresh request. Stopping server work requires a separate propagation contract; browser abort alone does not establish it.

## Assumptions and implementation order

1. **Reconcile current code before exact edits.** Compare this commit with the authoritative current revision and inspect the relevant lifecycle, result types, map handlers, server/worker and gateway contracts for drift. Locate existing tests and follow that checkout's instructions. Missing published tests or excerpts do not prove missing coverage.
2. **Define cancellation semantics.** Proposed default: cancel on panel close, unmount, and actual map/atlas replacement; keep ordinary selection, pan/zoom and scope exploration compatible with the existing retained-answer behavior. Define whether changing diagram surface counts as map replacement. Capture map identity plus a request generation, account and controller. Completed turns remain; pending cancelled turns are removed. Define the server commit point: cancellation before persistence prevents a new turn; cancellation after commit cannot retract an already-saved turn.
3. **Harden the client contract.** Add a typed cancelled outcome, distinguish external cancellation from timeout, handle an already-aborted signal, and guarantee listener/timer cleanup. Check cancellation after readiness and during body parsing. Preserve existing successful answer, citation, retrieval and thread parsing.
4. **Wire App lifecycle.** Centralize cancellation, invalidate generation before aborting, and call it on all defined transitions. Check ownership/map identity before warming, result, persistence warning and announcement updates. Immediate cleanup should leave a reopened/new-map panel usable; an old finalizer must not clear a newer request. This extends the existing controller/account guard rather than relying on fetch honoring abort.
5. **Add server propagation only if stopping work is required.** Derive a per-request cancellation signal from premature connection termination; distinguish it from normal request-body completion. Pass it through `answerAskQuestion`, cancellable retrieval and gateway calls. Check it between awaits and before persistence/response. Keep ticket release and event cleanup in `finally`. Cancel queued work individually; for running/shared retrieval, at minimum discard the cancelled consumer and suppress downstream gateway work while specifying whether computation can actually stop. Inspect gateway transport before selecting its API.
6. **Preserve accounting.** Keep reported usage and costs already incurred even after cancellation. Client abort cannot guarantee zero provider charge, zero quota use, or receipt of final cost headers by an edge proxy. Resolve edge ledger settlement separately before claiming end-to-end cost cancellation.

## Observable validation

Use deterministic delayed fake retrieval/gateway/fetch fixtures, then exercise the running browser flow; these are proposed checks, not tests executed here.

- Submit, close while readiness or POST is pending, then reopen: no late answer, timeout toast, warming indicator, announcement or local write; input can submit again.
- Submit on map A, change to B, start another request, then resolve A late (including a fake transport that ignores abort): B's pending state and thread remain correct. Test switching away and back to A to expose identity-only races.
- Change only selection/scope, pan or zoom: confirm the agreed retained-answer behavior. Repeat every real map replacement path and unmount/account change.
- Test an already-aborted signal, abort during response parsing, true timeout, network failure, unauthorized response and successful answer. Only true timeout shows timeout copy; successful citations/thread parsing stays intact.
- For server cancellation, stop at admission, queued retrieval, active retrieval, before gateway, during gateway and before persistence. Observe no downstream gateway call before cancellation, no pre-commit persisted turn, exactly-once ticket settlement, reusable worker capacity, and unaffected concurrent requests. Verify that cancellation cannot be swallowed into scope fallback.
- Verify actual usage/quota and edge settlement under connection loss. If active worker/provider computation continues, document that limit explicitly instead of presenting response suppression as stopped work.

The key risks are stale-result races, confusing map navigation with selection, cancellation swallowed by fallback, shared-worker damage, persistence racing cancellation and cost settlement after a disconnected client. Published evidence supports a concrete provisional design, but exact edit readiness and runtime correctness require the current-code and behavioral checks above.
